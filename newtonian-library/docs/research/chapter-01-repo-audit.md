## 3. Architectural observations for ch. 1 additions

### What fits cleanly

**A `coords` module is a pure leaf — the easiest possible addition.** Polar conversion and the acceleration decomposition depend only on `Vec3` and `<cmath>`; they touch no `Force`, no `State`, no integrator. It slots in exactly like `analytic/` does. Concretely, following the existing conventions:

- New namespace `newton::coords`, closed as `}  // namespace newton::coords` (hard rule 8). **Friction:** `DESIGN.md` hard rule 4 enumerates the permitted namespaces (`newton`, `newton::constants`, `newton::forces`, `newton::integrators`, `newton::analytic`, `newton::analysis`, `newton::systems`, `newton::io`) — `coords` is not on that list, and `DESIGN.md` is authoritative per `notes/00-start-here.md` ("If code and `DESIGN.md` ever disagree, `DESIGN.md` is right"). Rule 4, the file-by-file spec, and `include/newton/newton.hpp` (explicitly "the library's manifest") must all be amended in the same change. Note `docs/research/taylor-ch1-7-map.md` §1.4 already specifies this module, so this is a spec omission being corrected, not a scope expansion.
- Everything calls `std::sin`/`std::cos`/`std::atan2`, none of which are `constexpr` in C++17 — so every function must be plain `[[nodiscard]] inline`, with the C++-note precedent already written twice: `include/newton/core/vec3.hpp`'s `norm()` and `include/newton/analytic/projectile.hpp`'s file header.
- **Return-type choice worth deciding deliberately:** do *not* pack `(a_r, a_φ)` into a `Vec3`. `Vec3`'s whole API (`dot`, `cross`, `norm`) is Cartesian, so a polar pair wearing a `Vec3` invites silently meaningless calls. The library's own precedent for a named non-Cartesian tuple is `analytic::SHM` and `systems::RocketSample` (`struct RocketSample { double t, m, v, y; }`) — a small aggregate `struct PolarAccel { double a_r, a_phi; }` matches that. The `r̂`/`φ̂` unit vectors, by contrast, genuinely *are* Cartesian vectors and should return `Vec3`.
- **Test-harness friction, small but real:** `tests/test_util.hpp::close_vec3` is templated on "any type with public `.x`/`.y`/`.z`" (its C++ note says so). A `PolarAccel{a_r, a_phi}` will not work with `NT_CLOSE_VEC3` and needs two `NT_CLOSE` calls. Also inherit `tests/test_forces.cpp`'s convention of binding an `expected` local before passing it to `NT_CLOSE_VEC3` — the 3-parameter macro splits on top-level commas and misparses an inline `Vec3{1.0, 2.0, 3.0}` literal.
- **The build needs no edits.** `Makefile` discovers sources by `$(wildcard examples/*.cpp)` and `$(wildcard tests/*.cpp)`, and `HEADERS := $(shell find include -name '*.hpp')` is a blanket prerequisite — so `include/newton/coords/polar.hpp`, `examples/07_polar_coordinates.cpp`, and `tests/test_coords.cpp` are all picked up automatically. Same for `build.sh`.
- **The validation pattern already exists for this.** The most valuable ch. 1 test is the cross-check the research map §1.4 describes: run a Cartesian `simulate()` (say `forces::Spring` with `natural_length = 0`, or `PointGravity`), convert each recorded `State` to polar, and assert the numerically-differenced `(a_r, a_φ)` matches `(r̈ − rφ̇², rφ̈ + 2ṙφ̇)`. That is precisely the shape of `tests/test_numeric_vs_analytic.cpp`, so it lands in an existing file with an existing idiom.

**A Galilean transform also fits as free functions, with one teaching trap.** `State` is an aggregate of `(r, v, t)` and `Trajectory` is `(mass, states)` — both cheap to copy — so `boost(const State&, const Vec3& v_frame)` returning `{s.r - v_frame*s.t, s.v - v_frame, s.t}` and a `Trajectory` overload are three-line functions with no dependency on the integrators. Two notes:

- The *invariance test* is directly runnable today: simulate under `forces::UniformGravity` (velocity-independent), boost the ICs, simulate again, and check the two trajectories differ by exactly the boost. That works because `UniformGravity::operator()` ignores `v`.
- The trap, worth documenting rather than avoiding: `forces::LinearDrag`/`QuadraticDrag` are **not** invariant under a naive boost, because drag is defined relative to the medium, not the frame. A boosted drag simulation gives different physics unless the medium is boosted too. This is a genuinely good §1.4 lesson and the library is well positioned to demonstrate it — but it means a `boost()` on `Trajectory` cannot be advertised as "the physics is unchanged" without a caveat in the doc comment.

**Extending `newton::events` is friction-free.** `include/newton/simulate.hpp`'s `events` namespace uses one pattern — `[[nodiscard]] inline auto name(args) { return [captures](const State& s) { ... }; }` — and a ch. 1 addition (a turning point, an angular threshold for the half-pipe) drops straight in beside `ground_impact` and `apex`.

### Where the existing conventions actively resist ch. 1 additions

**1. The Force concept is single-particle, so pairwise forces need a second concept.** `Vec3 operator()(double t, const Vec3& r, const Vec3& v) const` receives no particle identity and no access to any other body. A pairwise force must be a different shape, e.g. `Vec3 operator()(double t, const Particle& a, const Particle& b) const`. That has a specific downstream consequence: **`forces::sum` cannot mix them.** `include/newton/forces/compose.hpp` returns `[fs...](double t, const Vec3& r, const Vec3& v) -> Vec3 { return (Vec3{} + ... + fs(t, r, v)); }` — the fold calls every pack element with `(t, r, v)`, so a pairwise callable will not compile inside it. Any `System` needs *two* force lists (per-body and pairwise) and either a second combinator or an explicit two-loop accumulation. `notes/04-extending.md` names the concept difference but not this `sum()` consequence.

**2. `Trajectory` and `simulate()` are structurally single-body.** `Trajectory` holds one `double mass`; `simulate(const Particle& p, Force&&, const SimOptions&)` takes one particle and one force. There is no plural output type — `include/newton/analysis/momentum.hpp`'s own C++ note documents this as a v0.1 limitation. Two consequences that are easy to miss:

  - `io::write_csv(path, const Trajectory&)` writes the fixed 7-column `t,x,y,z,vx,vy,vz` header, so multi-particle output must go through the generic `write_csv(path, column_names, rows)` overload (as `examples/02_projectile_drag.cpp` already does with a `series` tag column) or gain a new overload.
  - `analysis::energy_drift` and the whole `analysis/oscillation.hpp` trio take `const Trajectory&` and would need plural counterparts.

**3. The integrator step functions cannot be reused verbatim for a system state.** Every stepper is `State xxx_step(const State& s, double mass, double dt, Force&& force)` — scalar `mass`, single `State` — and `detail::dispatch_step(Method, const State&, double mass, double dt, Force&&)` in `simulate.hpp` hardcodes that shape in its four-case switch. An N-body loop therefore either (a) duplicates the four update equations, which `notes/04-extending.md` explicitly warns against ("build the N-particle version once and never maintain two integrator code paths"), or (b) templates the step functions on the state type so `State` and a new `SystemState` both satisfy them. Option (b) is the right call physically but touches four files that `DESIGN.md` specifies signature-by-signature, so it is a spec change, not a drop-in. Note also that a single particle then becomes the `N = 1` case — which is the research doc's recommendation but is a behavioural change to the tested API surface.

**4. `DESIGN.md`'s scope sentence is itself a blocker.** Line 15 reads "A **header-only C++17** library for simulating single-particle Newtonian mechanics." Adding a `System` contradicts the authoritative document's own scope statement, not merely its file list. Given `notes/00-start-here.md` establishes `DESIGN.md` as the contract, the honest sequencing is: amend `DESIGN.md` (scope sentence + hard rule 4's namespace list + a new file-by-file section) → update `include/newton/newton.hpp` → implement → test. The umbrella header and `DESIGN.md` are two halves of one manifest and drift apart silently otherwise.

**5. Constraint problems split into two very different difficulties.** The incline is *not* a library feature — it is a worked example expressible today with a hand-written lambda satisfying the existing Force concept (resolve `mg` into slope-parallel and slope-normal components; the normal force is whatever cancels the perpendicular part). It could ship as `examples/07_incline.cpp` with zero header changes. Atwood and a rigid pendulum are the opposite: they need the Lagrange-multiplier solver from `notes/04-extending.md`, which is a genuine v0.2 project. There *is* a cheap middle path worth considering for a ch. 1 pendulum — a stiff `forces::Spring` with `natural_length = L` as a penalty constraint, using existing machinery — but it needs an honest doc comment saying the rod is soft, and it interacts badly with `dt` (a stiff spring shortens the fastest timescale, and `SimOptions` is fixed-step by deliberate design, per `simulate.hpp`'s C++ note).

### Cheapest-to-highest-value ordering, given the above

1. `include/newton/coords/polar.hpp` + `tests/test_coords.cpp` + a `examples/07_polar_coordinates.cpp` that verifies the decomposition against a Cartesian `simulate()` run. Pure leaf, no existing file changes beyond `newton.hpp` and `DESIGN.md`; closes the largest single ch. 1 gap and the one the research map already specified.
2. A general constant-acceleration closed form in `newton::analytic` (`position(t, r0, v0, a)` / `velocity(t, v0, a)`), which `tests/test_integrators.cpp` currently inlines — trivial, and makes the sharpest ch. 1 integrator test callable from user code.
3. A uniform-circular-motion helper in `newton::analytic` (`centripetal_acceleration(v, r)` / `omega`), so §1.7's circular archetype has a ch.-1-framed oracle instead of only the §2.5 cyclotron functions.
4. Galilean boost free functions on `State`/`Trajectory` plus the drag-is-not-invariant lesson — small, and it is the only ch. 1 concept absent from both the code *and* the roadmap.
5. `examples/07_incline.cpp` — no header changes at all.
6. The `System` / pairwise-force work (items 1–3 of the friction list) — real design work, correctly scoped as v0.2 by `notes/04-extending.md`.
